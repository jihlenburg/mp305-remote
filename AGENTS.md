# AGENTS.md

Instructions for AI coding agents and human contributors working in this
repository. Read this file before changing anything.

## What this project is

A remote control for the ISDT MP305B bench power supply
(0 to 30 V, 0 to 5 A, 150 W). It has three parts that share one protocol
implementation:

- `mp305-core`, a Rust library with the device protocol, the Bluetooth LE and
  USB HID transports, and the device API (its design is decided at gate G3).
- `mp305-app`, a desktop tool for macOS, Linux and Windows built with egui.
- `mp305`, a Python library built on the Rust core with PyO3.

ISDT publishes no protocol documentation. The device firmware is the main
source of truth for the protocol. Findings from WebLink
(https://www.isdt.co/weblink/), from hardware, and from anywhere else come
on top of it. `docs/research/` labels every fact as confirmed in code (read
from the decompiled device firmware, or from the WebLink JavaScript),
confirmed on hardware (observed on the user's unit), or inferred.
"Cross-checked" means re-derived independently from the WebLink JavaScript.
A cross-check is a finding on top of the firmware, and it is not a hardware
confirmation. Where the firmware and another finding differ, the project
uses the firmware. For sources other than the device firmware, production
code relies only on items marked confirmed on hardware, or on items the
relevant DD file explicitly accepts as inferred with a TBD (ADR-0002).

Under Directive 2009/24/EC (2009/24/EG), decompiling the device firmware is
fully allowed in order to ensure full interoperability of `mp305` and
`mp305-app` with the device. There is no
limit on the information contained in that firmware. The library and the
desktop app use it to its fullest. The firmware image stays out of the
repository. Interoperability information reconstructed or gathered from it
stays in the repository, in whatever form it takes (LOGBOOK 2026-09-29,
"Firmware decompilation", "Firmware information", "Where firmware material
is kept", and "Firmware is the main source of truth").

## Process rules

This project follows the V-model described in
[docs/v-model/README.md](docs/v-model/README.md), approved by the user as
the process baseline on 2026-09-30. In short:

1. No production code for a module before its DD file
   (`docs/v-model/4-detailed-design/<module>.md`, the design plus its unit
   test specification) has passed gate G4. Gates pass only with the user's
   approval.
2. Write the test specification for a level together with the design for that
   level.
3. Write an ADR in `docs/adr/` for a decision that affects more than one
   module or product, picks between real alternatives the user might
   question, reverses an earlier decision, or changes a process rule. This
   includes such decisions made in chat. Choices local to one module go, with
   their rationale, into that module's DD file. Use the template in
   `docs/adr/README.md`.
4. A design item is an AR- or DD- entry. Every module names the design items
   it implements, and every automated test names its test specification ID
   (see Testing standards). A check script generates
   `docs/v-model/traceability.md` from the Parent columns, the test
   specification entries and these code tags. The output is committed and
   never edited by hand. The script is `scripts/check_traceability.py`;
   run it after any change to a requirement or test document and commit
   the regenerated file with the change. `--check` reports defects and an
   out-of-date matrix without writing.
5. Any change to an approved document (UR, SR, AR, DD or any test
   specification) needs the user's approval before the changed item is
   implemented or re-verified. Until then, set the item's Status to `changed`
   and note that approval is pending. Editorial changes that alter no
   requirement, design statement, expected result or ID are exempt and are
   logged as editorial in the revision table. Never fix a failing test by
   changing its specification without this approval. Before editing, use
   traceability.md to find the lower-level items and tests that depend on the
   changed item. The full procedure is in "Changing an approved document" in
   the process document.

## Task tracking

Keep these two files current during all work:

- [TODO.md](TODO.md) holds open and finished work, grouped by V-model phase.
  Update it when a task starts, finishes or turns out to be something else.
  Write dates, not session state ("started 2026-09-29", not "running").
- [LOGBOOK.md](LOGBOOK.md) records only what happened: what was done, what
  was decided and by whom, what was found, gate approvals (with the date and
  the commit hash of the approved documents) and verification runs (one line
  each, pointing to the run's record). Planned work goes in TODO.md. Routine
  test runs are not logged. Append new entries at the bottom. A second entry
  on the same day is a new `###` heading under that day's `##` date heading.
  Never rewrite old entries. If one turns out wrong, add a correction that
  names the heading it corrects.

## Git

- Never commit or push without the user's explicit permission. Stage and
  propose a commit message, then ask.
- One logical change per commit. Put the affected IDs in the message, for

- When the user permits the commit that holds a gate's approved documents,

## Functional safety and coding standards

[ADR-0008](docs/adr/0008-quality-standards.md) records the functional safety,
coding, documentation, coverage and HIL safety standards in this file. Changing
any of them needs a new ADR.

Because unintended or incorrect behavior of the power supply can cause direct
property damage (DUT destruction, electrical fire) and indirectly human injury,
this software is treated as an electrical safety-related system according to
**IEC 61508** (SIL 1/2 systematic fault avoidance). The codebase adheres to
MISRA-aligned safety guidelines tailored for Rust and Python:

Rust:
- `mp305-core` and `mp305-app` enforce `#![forbid(unsafe_code)]`. In
  `mp305-py`, any unavoidable PyO3 FFI is strictly isolated in a dedicated
  module with defensive preconditions.
- Zero panics in production: crates set
  `#![deny(clippy::unwrap_used, clippy::expect_used, clippy::panic)]`. Every
  fallible operation returns an explicit `Result` or `Option`.
- Defensive memory and slicing: crates set `#![deny(clippy::indexing_slicing)]`.
  Raw array/slice indexing is forbidden; use `.get()` with explicit handling.
- Safe arithmetic: crates set `#![deny(clippy::arithmetic_side_effects)]`. All
  setpoint scaling and protocol maths use checked or saturating operations.
- Crates set `#![deny(missing_docs)]` and
  `#![warn(clippy::missing_docs_in_private_items)]`. Clippy runs with
  `-D warnings` and pedantic safety lints. Private items must be documented to
  explain safety invariants.
- Every module starts with a `//!` comment that says what it does, why it
  exists, and which design items it implements, for example
  `//! Implements: DD-PROTO-001, DD-PROTO-002`.
- Public items document their purpose, units (volts, amps, and the device's
  raw scaling), and `# Errors` sections where relevant.
- Examples in docs compile as doctests. Use a mock transport so they run
  without hardware.
- Byte layouts of protocol frames are documented as tables in the rustdoc of
  the type that encodes or decodes them, with a link to the evidence in
  `docs/research/`.

Python:
- Every public module, class and function has a Google-style docstring and
  full type hints. The native module ships a `.pyi` stub.
- `mypy` runs with `strict = true`.
- Python API functions enforce runtime parameter validation and range clamping
  (for example, validating voltage in 0 to 30 V and current in 0 to 5 A) before
  calling into native Rust, providing defense-in-depth.
- Ruff runs with `E`, `W`, `F`, `B` (bugbear), `S` (bandit security) and `D`
  (pydocstyle, Google convention) rules.

Prose rules apply to all prose: Markdown documents (including TODO.md and
LOGBOOK.md), rustdoc, Python docstrings, code comments and commit messages.
- Plain, direct English. No em dashes or en dashes; use commas, colons,
  parentheses or separate sentences.
- Headings in sentence case.

## Testing standards

Cover as much as possible with unit tests. Design code so that it can be
tested without hardware: keep device I/O behind a transport interface and
test against a mock transport.

Test specifications and tags:
- Each test specification entry has its own ID (`AT-nnn`, `ST-nnn`, `IT-nnn`,
  `UT-<MODULE>-nnn`), lists the UR, SR or design item IDs it verifies, and
  names the automated test that implements it or gives a written manual
  procedure. The entry is the only record of what a test verifies.
- Unit test specifications sit in a "Unit test specification" section at the
  end of each DD file.
- An automated test names only its own spec ID: in Rust
  `/// Test: UT-PROTO-007` in the test's doc comment, in Python
  `@pytest.mark.spec("ST-014")`.
- These are defects: a UR, SR or design item without a test specification
  entry (or a recorded reason why demonstration, inspection or analysis is
  enough), a spec entry with neither an automated test nor a written manual
  procedure, and an automated test that names no spec ID.

A test's level comes from the ID it verifies, not from its directory:

| Level | Verifies | Where |
|---|---|---|
| Unit (UT) | DD | `#[cfg(test)] mod tests` next to the code, or `crates/*/tests/ut_*.rs` |
| Integration (IT) | AR | `crates/*/tests/it_*.rs`, Python: `tests/integration/` |
| System (ST) | SR | `tests/system/` (pytest, usually HIL) |
| Acceptance (AT) | UR | numbered manual steps in `docs/v-model/8-acceptance-tests.md`, automated parts in `tests/acceptance/` |

Code that doctests or `tests/` must reach lives in a library target:
`mp305-py` builds as `crate-type = ["cdylib", "rlib"]`, and `mp305-app` keeps
its logic in `src/lib.rs` with a thin `main.rs`.

Protocol tests and coverage:
- Protocol encode and decode get round-trip property tests (proptest) plus
  fixture tests built from hardware captures. A fixture test embeds the exact
  frames it needs inline and cites the capture file name and event timestamp
  in a comment. There is no copy of the captures under `crates/`.
- Python tests use pytest.
- Coverage is measured with `cargo llvm-cov` and `pytest-cov`. The targets
  per component are in ADR-0008. GUI drawing code is kept in `ui/` modules
  and excluded with `cargo llvm-cov --ignore-filename-regex`.
- Every coverage exclusion (`# pragma: no cover`, an ignore pattern, a file
  excluded as GUI drawing code) and every skipped or ignored test carries a
  comment giving the reason and, where one exists, the test or TODO item that
  covers it instead.
- A change that lowers a component's coverage, or leaves it below its target,
  states the reason in the commit message and the LOGBOOK.

### Verification records

A level counts as verified when every test specification entry of that level
has a recorded passing result, or a failure the user explicitly accepted as a
known deviation (logged, with a TODO item). A result can come from an
automated test (including HIL), a manual procedure, inspection, demonstration
or analysis. Each verification run gets a record in
`docs/v-model/records/YYYY-MM-DD-<level>-<scope>.md` with the commit hash (or
`uncommitted` plus a diff summary), OS, transport, the device firmware version
for hardware runs (or a pointer to the LOGBOOK entry that records it), the
exact command or procedure, and pass or fail per test ID.

System tests run on real hardware over each transport the SRs name.
Acceptance tests are validation: they run against a release build (app binary
and installed wheel) and a real MP305B, and the user performs or witnesses
them. An agent may prepare and assist, but never records an AT as passed on
its own.

## Working with the real device

A power supply can destroy whatever is connected to it. HIL tests, and spikes
that talk to a device, follow these rules:

- Nothing is connected to the output unless the test or spike says so.
- Defaults stay at 5 V or less and 100 mA or less unless the test documents
  why it needs more.
- The output is off at the end, including on failure. Tests do this in their
  teardown.
- Device settings that are changed are restored afterwards.
- An agent never sets `MP305_HIL` unless the user asks for it in the current
  session. A spike needs the user's go-ahead before any command that changes
  device state.

### Hardware-in-the-loop tests

HIL tests run only when `MP305_HIL=1` is set and `MP305_HIL_DEVICE` names the
unit: the Bluetooth peripheral identifier as the OS reports it (for example
the macOS CoreBluetooth UUID), or the HID serial number or path. The tests
enforce this themselves and connect only to that unit.

- Rust: HIL test names start with `hil_`, the tests carry
  `#[ignore = "HIL: needs a real MP305B"]`, and each one first calls the
  shared `hil_device()` helper. The helper panics, failing the test before
  any I/O, unless both variables are set. `#[ignore]` is used for nothing
  else.
- Python: HIL tests carry `@pytest.mark.hil`. `pyproject.toml` registers the
  `hil` and `spec` markers and sets
  `addopts = "-m 'not hil' --strict-markers"`, so a plain pytest run leaves
  them out. A `conftest.py` fixture skips them unless both variables are set,
  and connects only to `MP305_HIL_DEVICE`.

The run commands are in the Commands section.

### Spikes

A spike is a throwaway experiment that answers one question, for example
"does the device answer this frame?". Each spike has its own folder under
`spikes/` with a README that states the question. Spikes stay outside the
Cargo workspace (`exclude = ["spikes"]`) and the Python package, and the
documentation, lint and coverage rules do not apply to them. Production code
never imports or copies spike code; it is written from the approved DD file.
The answer goes into `docs/research/`, and a LOGBOOK entry describes the run.

### Captures and firmware version

Raw hardware captures live once, in `docs/research/captures/`, as written by
the spike that recorded them (JSONL with a meta line, events and results).
They are evidence and are never edited after recording. A correction is a new
capture or a note. Each capture is described in a LOGBOOK entry with the date,
the transport, what was sent, and the firmware version or a pointer to the
entry that records it.

The device reports its versions in the `0xE1` reply to `0xE0`, also over
Bluetooth. Bytes 1 to 4 after the opcode are the main firmware version, which
WebLink labels "System Version", and bytes 13 to 16 are what WebLink labels
"Firmware Version" (LOGBOOK 2026-09-29, "Corrections, second round"). Record
both in the LOGBOOK with the date and cite that entry from captures and
hardware runs. Read them again after any firmware update. Which chip each
version belongs to is inferred.

## Commands

The workspace does not exist yet. Once it does, the expected commands are:

```sh
python3 scripts/check_traceability.py --check
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo llvm-cov --workspace
uv run maturin develop -m crates/mp305-py/Cargo.toml
uv run --no-sync pytest
uv run --no-sync ruff check
uv run --no-sync mypy python/mp305
```

`--no-sync` stops uv from reinstalling a cached older build of the extension
over the one `maturin develop` just built. Without it, the Python tests can
pass against stale Rust code.

HIL tests, only when the user asks for them in the current session:

```sh
MP305_HIL=1 MP305_HIL_DEVICE=<id> cargo test --workspace -- --ignored hil_
MP305_HIL=1 MP305_HIL_DEVICE=<id> uv run --no-sync pytest -m hil
```

Update this section when the real commands differ. Add the exact
`--ignore-filename-regex` pattern for `ui/` modules to the `cargo llvm-cov`
line once the layout exists.
