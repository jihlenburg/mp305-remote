# App controls and recording with the USB lamp

Date: 2026-10-05. Exploratory hardware check under ADR-0019, not a system or
acceptance matrix run. Commit: uncommitted on
`2528dabe26ca43a08994e11ed2367fa2647b401f`. Diff: app DD revision 5 UI and
names implementation; the working tree also has the pre-existing USB owner
thread fix. OS: macOS 27.0.1 (26A434), arm64. Transport: USB HID,
`DevSrvsID:4295529386`. System version: 1.6.0.51, read during this run.
The Bluetooth firmware version remains 2.0.2.0 from LOGBOOK 2026-10-05,
the release checks preceding "USB and the app meet the real supply".

The user authorised output switching with the attached 12 V, 1 W LED lamp.
The initial reading confirmed DC mode, output off and 12.00 V / 0.200 A
setpoints. These are also the enforced user limits for the connection; the
higher-than-default limits are necessary for the authorised 12 V lamp.

## Method

The Mac was locked, so native window input was unavailable. The exploratory
spike `spikes/hardware_ui` instantiates the real `mp305_app::ui::App` with
AppCore, Shell and the production USB worker. egui_kittest clicks and types
into the production controls. Its event relay observes and forwards the
worker events unchanged. Discovery returns only the named USB endpoint.
No Bluetooth connection, native window, mock transport or acceptance witness
is involved. The local name service is outside this harness; its persistence
and app integration are covered by UT-APP-032 and UT-APP-033.

Exact command:

```sh
MP305_HIL=1 MP305_HIL_DEVICE=DevSrvsID:4295529386 CARGO_TARGET_DIR=target \
cargo run --manifest-path spikes/hardware_ui/Cargo.toml \
  > docs/research/captures/2026-10-05-ui-usb-01.jsonl \
  2> /tmp/mp305-hardware-ui-run-01.log
```
