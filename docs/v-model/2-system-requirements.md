# 2. System requirements (SR)

Status: approved (G2, user, 2026-09-30; SR-007 changed and approved 2026-09-30, revision 11)

This draft refines revision 8 of
[1-user-requirements.md](1-user-requirements.md), which has not passed G1.
It is written ahead of G1 and is not put up for G2 until G1 has passed; any
change to the URs at G1 flows into it first. Revision 8 of this document
rewrites the requirements from the device firmware findings, as the user
decided on 2026-09-30 (LOGBOOK, "Requirements go back to the drawing
board").

The system is `mp305-core` together with the two products built on it, the
app `mp305-app` and the Python library `mp305`. A requirement that names
neither product applies to both. Device facts cite
[docs/research/device-model.md](../research/device-model.md) by section,
which carries the evidence label of each statement (code, hardware,
inferred), and [docs/research/protocol.md](../research/protocol.md). A fact
labelled "code" was read from the 1.6.0.51 update and is not yet checked on
the user's unit, which reported 1.6.0.40; the SR names the TBD that settles
it. "Frame" means the framed request or reply of protocol.md 2. "Reading"
means a decoded `0xC3`.

TBD-017 was settled on 2026-09-30: automatic reconnection is opt-in per
session (SR-055) and the bench-safety note recommends USB.

## 1. Discovery and connection

| ID | Requirement | Parent or source | Priority | Verification | Status | Rationale |
|---|---|---|---|---|---|---|
| SR-001 | Bluetooth discovery shall report every peripheral whose advertised local name starts with `0000MP30` or whose manufacturer data carries company `0xABBA` and the bytes `AF FA`, with: the identifier the OS assigns, the name as advertised, the unit identifier (the last three characters of the name), whether the name carries `S` at index 12 (remote control enabled on the supply), and the signal strength in dBm. | UR-001, UR-002, UR-010 | must | T | approved | device-model.md 1: name layout, unit characters and manufacturer data (code; the name and the first 10 manufacturer bytes hardware). |
| SR-002 | Bluetooth discovery shall scan for 10 s by default. The scan time shall be settable from 1 s to 60 s. | UR-001, UR-027 | must | T | approved | The advertising interval is 500 ms (device-model.md 1, code), but advertisements arrived several seconds apart on macOS (hardware). |
| SR-003 | USB discovery shall report every HID device with vendor ID `0x28E9` and product ID `0x028A` whose product string contains `MP305`, with its HID device path as the unit identifier. It shall not expect a serial number string. | UR-001, UR-002, UR-010 | must | T | approved | device-model.md 1 and 2.2 (code): the serial string request stalls; the product string is `MP305B` on 1.6.0.51. Not yet seen on hardware (TBD-013). |
| SR-004 | The system shall connect only to the supply the caller names by identifier. The library may connect without an identifier only when discovery found exactly one supply, and shall raise an error naming the supplies found otherwise. The app shall never connect without a user selection. | UR-002, UR-010, H-002 | must | T | approved | Two units differ only in the three unit characters over Bluetooth and in the device path over USB (device-model.md 1). |
| SR-005 | When discovery finds no supply, the app message and the library exception text shall name the possible causes: the supply is off or out of range, another app (WebLink in a browser, ISDT's Polying app) is connected to it, a USB host is talking to it, or remote control is disabled on the supply. | UR-027 | should | T | approved | The supply does not advertise in any of those states (device-model.md 1 and 4.3, code; connected elsewhere hardware). |
| SR-006 | The system shall send nothing to a supply other than these requests: `0x18` (bind, Bluetooth only), `0xE0`, `0xC2` and `0xC8`. | SR-048 | The system shall hold at most one connection to a given supply at a time, over one transport, and shall tell the user when a Bluetooth connection is refused or goes silent because a USB host is active. | UR-001, UR-027 | must | T | approved | device-model.md 4.3 (code): USB traffic silences Bluetooth for 8 s, a bound Bluetooth host detaches USB, a second central is dropped. |

## 2. Authorization over Bluetooth

| ID | Requirement | Parent or source | Priority | Verification | Status | Rationale |
|---|---|---|---|---|---|---|
| SR-007 | After a Bluetooth connection is made, the system shall enable notifications on `AF01` and `AF02`, verify that the negotiated ATT MTU carries the longest reply (71 bytes plus the ATT header) and fail the connection otherwise, and then write the bind frame to `AF02`: `0x18`, the 16-byte host ID of SR-049, two zero bytes, and the fast flag. It shall send nothing else until the bind reply arrives or the wait ends. | UR-008, UR-032 | must | T | approved | device-model.md 2.1 and 4.1 (code; the WebLink frame and its replies hardware). The host stack negotiates the MTU on its own and `btleplug` offers no request (TBD-021, settled 2026-09-30); the device accepts up to 247. WebLink's 1000 ms pause has no counterpart in the firmware and is dropped. |
| SR-049 | Each product installation shall generate a random 16-byte host ID once, store it in the user's state directory, and present the same ID at every bind. The ID shall not be all zero and shall not be WebLink's constant ID. | UR-032, H-006 | must | T | approved | The supply remembers up to five host IDs (device-model.md 3 and 4.1, code; verified on the CH58x code 2026-09-30, TBD-006 on hardware). A per-installation ID keeps two hosts apart, which WebLink's constant ID does not. |
| SR-050 | The system shall first send the bind with the fast flag set. On `19 00` the connection is allowed without a prompt and the user is told that the supply recognised the host. On `19 FF` the system shall send the bind again with the fast flag clear, tell the user to confirm on the supply's screen (SR-008), and wait for the reply. | UR-008, UR-032 | should | T | approved | device-model.md 3 and 4.1 (code): the fast reply comes from the Bluetooth chip without a prompt; a bind with the flag clear is forwarded to the prompt. The order lets a remembered host connect with no one at the bench. TBD-006 on hardware. |
| SR-008 | While waiting for a bind reply that needs the prompt, the app shall show "Confirm the connection on the supply's screen within 30 seconds", and the library shall log the same text through Python's `logging` module at level WARNING and call an optional callback the caller passes. | UR-008 | must | T | approved | A person must press allow on the supply (device-model.md 4.1; hardware). The supply drops an unbound link about 30 s after connecting (code, TBD-008), so the user needs the bound. |
| SR-009 | The system shall wait for the bind reply until it arrives, the link drops, or 30 s have passed since the connection was made, whichever is first. On timeout or link drop it shall disconnect and report a timeout naming the 30 s bound. The bound shall not be settable above 30 s. | UR-008, UR-016 | must | T | approved | device-model.md 4.1 (code, TBD-008): the Bluetooth chip terminates an unbound link at about 30 s; a longer wait cannot succeed. Replies took 3.0 s, 3.6 s and 7.7 s with a person ready (hardware). |
| SR-010 | The system shall treat the connection as allowed only when the bind reply is exactly `19 00`. On any other reply it shall report "denied", send nothing more, disconnect, and not reconnect by itself. | UR-008, UR-016, H-006 | must | T | approved | `19 FF` is the deny reply (hardware). There is no read-only mode after a deny (TBD-001, settled). |
| SR-011 | Over USB HID, the system shall not send a bind and shall treat the connection as allowed once the supply answers `0xE0`. | UR-008, UR-036 | must | T | approved | device-model.md 4.2 (code, TBD-004): the Bluetooth chip has no bind logic for USB and remote control is granted without a prompt. |

## 3. State and readings

| ID | Requirement | Parent or source | Priority | Verification | Status | Rationale |
|---|---|---|---|---|---|---|
| SR-012 | After an allowed connection, the system shall read `0xE1` and one `0xC3`, and report model, application version, hardware revision, setpoints, output state, regulation mode, live mode and faults before it accepts any control request. | UR-004, UR-026 | must | T | approved | device-model.md 1 and 8. Over Bluetooth `0xE1` is version, model, hardware (hardware); over USB it is model, 8 bootloader bytes, version, name (code, TBD-010). |
| SR-013 | While connected, the system shall request `0xC2` continuously, sending the next request no earlier than 100 ms after the previous reply, and shall deliver at least 2 readings per second over each transport. | UR-011, UR-028 | must | T | approved | WebLink paces with 100 ms after each reply. One cycle took about 225 ms over Bluetooth (hardware). |
| SR-051 | Over USB, the system shall send a frame to the supply at least every 2 s while connected, also while polling is paused, and shall use the `0xC2` poll for this whenever it runs. | UR-035, H-004 | must | T | approved | device-model.md 4.4 (code): 8 s without a frame drops the USB link and releases remote control. 2 s leaves margin for stalls. |
| SR-014 | Each reading shall carry a host timestamp taken when the reply arrived, and values converted as follows: voltages raw / 100 in V, currents raw / 1000 in A, power raw / 100 in W, energy raw / 10 in Wh, working time raw in s, temperature as a signed 8-bit value in °C. | UR-003, UR-017, H-005 | must | T | approved | device-model.md 8 (code for the producers; setpoints, output, percentage, temperature, time, energy and power hardware with the output off). Measured voltage and current are TBD-011. |
| SR-015 | The system shall report the regulation mode as "off" for `outState` 0, CV for 1, CC for 2, "held above setpoint" for 3, and "unknown" with the raw value for anything else. | UR-011, UR-017 | must | T | approved | device-model.md 8: 0 output off (code), 1 and 2 (code), 3 inferred. |
| SR-016 | The system shall drop any frame whose length is shorter than its layout needs, whose checksum or length field is wrong over USB, or whose leading byte on `AF01` is not `0x31`, count it, and log it. It shall never turn part of a frame into a reading. | UR-017, UR-034, H-005 | must | T | approved | A half-decoded frame would show wrong values. The `0x31` is the constant route tag on `AF01` replies (device-model.md 2.1, code and hardware). |
| SR-017 | Each connection shall have at most one request in flight, and the next request shall not be sent before the reply to the previous one arrived, or its timeout passed. An arriving frame shall be dispatched by its opcode: the reply to the request in flight (request + 1) completes it; `0xC5`, `0xDD`, `0xE5`, `0xEB` and `0xDB` are accepted at any time and reported as device events; a `0x19` or `0xC9` that arrives without a matching request in flight is reported as a device event and never attributed to a later request. Any other frame is counted and logged. | UR-034, H-001, H-005 | must | T | approved | device-model.md 6 (code): the bridge holds one frame per direction, the supply sends frames on its own, and bind and remote-control replies can arrive seconds later. Unsolicited frames are not yet captured on hardware (TBD-018). |
| SR-052 | Every request shall carry its complete payload as protocol.md 4 lists it; the system shall never send a shorter frame. | UR-034, H-001, H-003 | must | T | approved | device-model.md 6 (code): request lengths are not checked, and a short request is completed with stale bytes from an earlier one. |

## 4. Control

| ID | Requirement | Parent or source | Priority | Verification | Status | Rationale |
|---|---|---|---|---|---|---|
| SR-018 | Before its first control command on a connection, the system shall send `0xC8` with `remoteCon = 2` built from the latest reading. Over USB it shall proceed only if `0xC9` returns 0 within 1 s. Over Bluetooth it shall expect no immediate reply, tell the user to confirm remote control on the supply's screen (SR-053), and proceed only when a `0xC9` with status 0 arrives; status 1 is reported as denied. Later commands shall use `remoteCon = 1`. | UR-036, UR-023 | must | T | approved | device-model.md 5 (code, TBD-012): USB grants at once, Bluetooth opens "Allow Remote Control" and answers later; a denial or a 60 s silence gives status 1. |
| SR-053 | While a remote-control request over Bluetooth is pending, the app shall show "Allow remote control on the supply's screen" and the library shall log the same text at level WARNING and call the optional callback of SR-008. The system shall send no other control command while the request is pending, and shall report a denial if no `0xC9` arrives within 70 s. | UR-036 | must | T | approved | device-model.md 5 (code): every control command is silent while the request is pending; the prompt closes as denied after about 60 s. |
| SR-019 | The system shall build every `0xC8` from a reading that arrived after the previous `0xC9` and is at most 1 s old, reading `0xC3` first if it has none. It shall copy every field from that reading and change only the field the request names; `refresh` shall be 0. | UR-023, UR-005, H-001, H-003 | must | T | approved | `0xC8` carries the whole state and applies it field by field (device-model.md 9, code; TBD-012). SR-022 is the one exception. |
| SR-020 | The system shall set `output = 1` only in a command that carries an explicit output-on request. | UR-005, H-001 | must | T | approved | Together with SR-019 this keeps the output off unless the user asks. |
| SR-021 | The system shall reject control requests with a mode error while the latest reading reports `model` other than 0 (DC), and shall always send `model = 0`. It shall never request a mode change. | UR-023, UR-004, H-001 | must | T | approved | A `0xC8` in another mode is rejected by the supply, and a different `model` requests a mode change (device-model.md 7, code). |
| SR-022 | An output-off request on an allowed connection in DC mode shall be sent ahead of any queued request, built from the latest reading whatever its age with only `output` set to 0, and the supply's `0xC9` acknowledgment shall arrive within 0.5 s of the request. If remote control was lost or never taken, the system shall first request it (SR-018) and tell the user that, over Bluetooth, this needs a confirmation on the supply. The system shall then read `0xC3` and report any setpoint that differs from what the user last saw. | UR-006, H-004 | must | T | approved | Speed beats freshness here: with the output off, a stale setpoint is harmless until the next output-on. The Bluetooth confirmation is a device property the software cannot avoid (device-model.md 5, code). |
| SR-023 | The system shall handle `0xC9` as follows: 0 accepted; 1 remote control not granted or lost, reported as such and all control disabled until the user requests control again; `0xFF` rejected, reported with the reason the system can infer (mode, range, fault, busy); any other value rejected, reported with the value. Except while a Bluetooth remote-control request is pending (SR-053), no reply within 1 s shall be reported as a timeout, with the device state unknown until the next reading. | UR-016, H-001; user, conversation 2026-09-29 (1 s) | must | T | approved | device-model.md 9 (code, TBD-012). Read replies took up to 135 ms on hardware. |
| SR-024 | The system shall reject, before encoding, any setpoint that is not a finite number, is negative, exceeds the supply's range, or exceeds the user limit of UR-007. It shall round accepted values to the nearest 10 mV or 1 mA. | UR-007, UR-012, H-005, H-007 | must | T | approved | NaN or a negative value would otherwise wrap into a large raw `u16`. |
| SR-025 | The supply's setpoint range shall be 0 to 30.00 V and 0 to 5.000 A until TBD-003 settles it. | UR-012 | must | T | approved | The firmware accepts up to 30.50 V and 5.100 A (device-model.md 9, code); the rated values are the safer choice until the output at the top is measured. |
| SR-026 | The system shall reject an output-on request while the latest reading reports any fault. | UR-009, H-008 | must | T | approved | The supply refuses it too (device-model.md 8, code); refusing first avoids a `0xFF` and a partial apply. |
| SR-054 | The system shall release remote control with `0xC8`, `remoteCon = 0`, only while the latest reading reports DC mode. | UR-018, UR-006 | must | T | approved | device-model.md 5 (code): a release sent in another mode is rejected and the grant stays. |

## 5. Faults and link loss

| ID | Requirement | Parent or source | Priority | Verification | Status | Rationale |
|---|---|---|---|---|---|---|
| SR-027 | The system shall decode `chargeError` bits 0 to 8 into named faults (reversed output, low battery, battery too cold, battery overheat, system overheat, over-current, over-voltage, power-stage start failure, output voltage failure) and report any of bits 9 to 15 as "unknown fault bit n". Every change in the set of active faults shall be reported with the reading that shows it. | UR-009, H-008 | must | T | approved | device-model.md 8 (code): bits 9 to 15 are never set in `0xC3`; only 0 seen on hardware. |
| SR-028 | The system shall declare the link lost on an OS disconnect event, a transport error, or three `0xC2` polls in a row without a reply within 1 s each, and shall report it within 4 s of the last reply, saying that the output is still in its last state and that the supply has released remote control. After that it shall send nothing and not reconnect until the user asks, unless automatic reconnection is enabled (SR-055). | UR-024, H-004 | must | T | approved | device-model.md 4.4 (code, TBD-005). |
| SR-055 | Automatic reconnection shall be off by default and enabled per session by the user. When enabled and the link is lost, the system shall retry the connection to the same identifier every 5 s for up to 10 min, over Bluetooth with the fast bind only (SR-050 without the prompt step), and after a successful connection repeat SR-012 and resume polling. It shall not send `0xC8` until the user issues a new control request, and it shall report each reconnection. | UR-037, H-003, H-004 | should | T | approved | An unattended log run survives a short link loss. Without a remembered host the fast bind gets `19 FF` and the retry stops with a report; a prompt would need a person anyway. |
| SR-029 | When a library connection closes (`close()` or the end of a `with` block) on an allowed connection in DC mode, the library shall switch the output off as in SR-022, then send `0xC8` with `output = 0` and `remoteCon = 0`, and then disconnect, whether or not the script ever took remote control. An error during this shall be logged and shall not hide an exception already in flight. | UR-018, UR-006, H-004 | must | T | approved | The supply keeps the output on and only releases the grant when the link drops (device-model.md 4.4, code). The app's behavior is SR-030. |
| SR-030 | When the user disconnects in the app or closes its window while the output is on, the app shall ask whether to switch the output off. Either way it shall then send `0xC8` with `remoteCon = 0` (and `output = 0` if chosen) before disconnecting. | H-004, UR-006 | should | D | approved | Some users want a DUT to stay powered after the app closes; nobody should lose that choice by accident. |

## 6. Python library

| ID | Requirement | Parent or source | Priority | Verification | Status | Rationale |
|---|---|---|---|---|---|---|
| SR-031 | Every library call shall block until done or timed out, release the GIL while waiting, and raise `KeyboardInterrupt` within 0.5 s of Ctrl-C. | UR-015 | must | T | approved | ADR-0007 (proposed). |
| SR-032 | The library shall raise these exceptions, all derived from `mp305.Mp305Error`: `NotFoundError`, `ConnectionDeniedError`, `SetpointRangeError` (also a `ValueError`), `CommandRejectedError`, `RemoteControlDeniedError`, `RemoteControlLostError`, `ModeError`, `FaultActiveError`, `Mp305TimeoutError` (also a `TimeoutError`) and `LinkLostError` (also a `ConnectionError`). | UR-016 | must | T | approved | One type per case of UR-016 plus the cases SR-021, SR-023 and SR-026 add. Denied and lost remote control are separate because the supply decides them at different times. |
| SR-033 | A reading shall be an immutable typed object with: timestamp (float, seconds since the epoch), voltage, current, power (float, V, A, W), set_voltage, set_current (float, V, A), output_on (bool), mode (enum OFF, CV, CC, HELD_ABOVE, UNKNOWN), live_mode (enum DC, PROGRAM, PD, CHARGE), faults (frozenset of a fault enum), temperature (int, °C), energy (float, Wh) and working_time (int, s). | UR-017 | must | T | approved | Immutable readings can be shared between threads and stored in lists without copying. |
| SR-034 | The library shall offer a blocking iterator of readings at a requested rate from 0.1 to 4 per second, and a helper that writes the stream to CSV for a given duration or until interrupted. If the transport cannot keep up, the iterator shall deliver what it gets and log one warning. | UR-028 | must | T | approved | 4 per second is about what Bluetooth delivers (SR-013). A silent shortfall would corrupt a timed log. |
| SR-035 | The ramp helper shall take the quantity (voltage or current limit), start, stop, step and dwell time, check every point against SR-024 before sending the first, and stop at the first error or `KeyboardInterrupt`, leaving the output as it is. | UR-029 | could | T | approved | Checking all points first means a bad end value fails before the DUT sees any step. |
| SR-036 | The library shall ship as wheels for CPython 3.10 and later on macOS 13 and later (arm64, x86_64), Linux manylinux_2_35 (x86_64, aarch64; Ubuntu 22.04 and later) and Windows 10 22H2 and later (x86_64), with a `.pyi` stub for the native module. | UR-015, UR-021 | must | I | approved | Minimum OS versions settled by the user on 2026-09-30 (TBD-014). |

## 8. Transport framing (derived)

| ID | Requirement | Parent or source | Priority | Verification | Status | Rationale |
|---|---|---|---|---|---|---|
| SR-044 | Over Bluetooth, the system shall write `0x12, opcode, payload` to `AF01` and `opcode, payload` to `AF02`, with write-with-response and one write in flight, and shall accept notifications as `0x31, opcode, payload` on `AF01` and `opcode, payload` on `AF02`. It shall treat every notification as one whole frame. | derived, UR-034 | must | T | approved | device-model.md 2.1 (code; requests without payload hardware). The leading `0x12` is a placeholder the Bluetooth chip discards; the `0x31` is a constant route tag. Writes with a payload (`0xC8`) are code only (TBD-012). |
| SR-045 | Over USB HID, the system shall send each frame as one or more output reports `01, n, n stream bytes` with `n` from 1 to 62, starting every frame in a new report and never sending a frame before the reply to the previous one arrived. The stream is `AA 12 len opcode payload sum` with every `AA` after the first doubled. It shall reassemble input reports `02, n, n stream bytes` by concatenating the `n` bytes of each report, undoubling `AA` pairs, and checking the length field and the checksum, and shall expect address `0x21` in replies. | derived, UR-034 | must | T | approved | device-model.md 2.2 (code): the byte after the report ID is the number of valid bytes in that report; two frames in one report, or a frame started before the previous reply, can be forwarded corrupted with a valid checksum. WebLink's 61-byte stride and its 5 ms pause are one valid choice, not a requirement; its de-doubling bug must not be copied (protocol.md 1.1). Not yet seen on hardware (TBD-013). |
