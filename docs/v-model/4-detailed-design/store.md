# DD: store module of `mp305-core`

Status: approved (G4 store, user, 2026-10-01, revision 2; revision 3 approved 2026-10-01, revision 4 approved 2026-10-02)

Refines AR-033 of [3-architecture.md](../3-architecture.md) (approved at
G3). Device facts cite
[docs/research/device-model.md](../../research/device-model.md) with their
evidence labels. The module keeps the per-installation state on disk: the
16-byte host ID the bind presents (SR-049) and one unclean-exit marker per
supply identifier (SR-046). It implements the `session::Markers` trait
(DD-SESS-001) and hands the host ID to the product, which passes it to
`Session::connect`. The products choose the directory (AR-033: the user's
state directory from the `directories` crate; note for the product DDs:
`ProjectDirs::state_dir()` is `Some` only on Linux, so the app and the
library fall back to `data_local_dir()` on macOS and Windows); the module
never decides a path itself. Coverage target 85 % (ADR-0008, "rest of
`mp305-core`"); everything here runs on a temporary directory in tests.
Revision 2 resolves the independent review of revision 1 (LOGBOOK, "Store,
csv and discovery design reviews").

Rust module tree: `mp305_core::store` with `mod.rs` (`Store`, the host ID
and the `Markers` impl, all `pub` so that IT-033 reaches them), `names.rs`
(pure: the identifier to file name mapping) and `files.rs` (the atomic
write and the create-if-absent write). Every source file starts with
`//! Implements: DD-STORE-nnn`. Dependencies: `getrandom` 0.4 (the OS
random source; already in `Cargo.lock` through other crates), `tempfile`
as a dev dependency (also already in the lock). Both are put to the user
in section 4.

## 1. The store

| ID | Design item | Refines | Status | Rationale |
|---|---|---|---|---|
| DD-STORE-001 | `Store::new(dir: impl Into<PathBuf>) -> Store` does no I/O. The directory and its `markers` subdirectory are created with `create_dir_all` on the first write (a concurrent creation is tolerated by std). Files: `<dir>/host_id` holding 32 lowercase hex characters and a newline; `<dir>/markers/<name>.marker` (DD-STORE-005) holding two lines, the marker time as decimal seconds since the Unix epoch and the supply identifier as given. `files::write_atomic(path, bytes)`: the content goes to `<path>.<pid>-<n>.tmp` in the same directory (`n` from a process-wide counter), opened with `create_new`, written, `sync_all`ed, then `rename`d over `path`; rename replaces the file in one step (POSIX `rename`, Windows `MoveFileEx` with replace), so with the `sync_all` before it a crash leaves the old content or the new, never a part. A Windows sharing violation on the rename (another process holding the target open) is `Error::Store`, like every I/O failure: `Error::Store { message }` (DD-SESS-060) with the path and the OS error text. Logging under `target: "mp305_core::store"`. | AR-033 | approved | A per-process temp name keeps the app and a script, or two scripts, from writing into each other's temp file; `sync_all` is what makes the rename meaningful after a power loss on ext4 and APFS. Decimal seconds need no calendar code and round-trip exactly. |
| DD-STORE-002 | `host_id(&self) -> Result<HostId, Error>` reads `host_id` and parses it: (1) decode as UTF-8 (reason `not utf-8`); (2) `trim_ascii()`; (3) length 32 (reason `length <n>`); (4) every byte `is_ascii_hexdigit()`, either case (reason `not hex`); (5) decode with `chunks_exact(2)` and `HostId::new` (reason `rejected`). A valid file gives its ID. A missing file (`NotFound`) gives a new ID created as DD-STORE-003 says, logged at INFO (`host id created <path>`). A file whose content fails (1) to (5) is replaced by a new ID, logged at WARN (`host id replaced: <reason>`). Any other read error (permission, a sharing violation) is `Error::Store` and writes nothing. Every call reads the file; nothing is cached. | AR-033 | approved | SR-049: one ID per installation, stable across restarts, never all zero, never WebLink's. A corrupt file regenerated with a warning is AR-033's rule; a transient error must not destroy a valid ID, since the supply would then prompt again and use one of its five slots (device-model.md 3 and 4.1, code). |
| DD-STORE-003 | Generation and first write. `generate_with(fill: impl FnMut(&mut [u8]) -> Result<(), getrandom::Error>) -> Result<HostId, Error>` fills 16 bytes up to three times until `HostId::new` accepts them; a third rejection or a `fill` error is `Error::Store` (the error's text included). `host_id` calls it with `getrandom::fill`. The first write uses `files::write_if_absent(path, bytes) -> io::Result<bool>` (`true` when it created the file, `false` when the file existed; the temp file is removed either way): the temp file as in DD-STORE-001, then `hard_link(tmp, path)`, which creates `path` only if it does not exist and publishes content that is already complete and synced; on a hard-link error other than `AlreadyExists` (FAT, exFAT and some network shares support no hard links) it falls back to opening `path` with `create_new` (`O_EXCL`, `CREATE_NEW`, also create-if-absent), writing and `sync_all`. `create_or_adopt(path, generated: HostId) -> Result<HostId, Error>` calls it and, when the file existed, reads and parses the existing file as DD-STORE-002 says, adopting its ID (a corrupt one is then replaced with `write_atomic`; two processes that both find a corrupt file both replace it and the last wins, an accepted window). `files::temp_path(&Path) -> PathBuf` builds the temp name. | AR-033 | approved | SR-049; the OS random source is the only source good enough for an ID that keeps two hosts apart; the rejected values have probability 2 to the power of minus 127. Two processes that start on an empty directory at once must end with one ID, and a hard link (`linkat` on APFS and ext4, `CreateHardLinkW` on NTFS, all failing with `AlreadyExists`) publishes complete content in one step, and `create_new` is the fallback where links are unsupported. |
| DD-STORE-004 | `impl session::Markers for Store`. An identifier can be stored when the marker file can give it back unchanged: it is not empty, it contains neither `\n` nor `\r`, and it has no ASCII whitespace at its start or end (`trim_ascii` leaves it unchanged); `names::storable(identifier: &str) -> Result<(), &'static str>` is pure and gives the reason `empty`, `line break` or `surrounding whitespace` (checked in this order, so a trailing `\r` or `\n` is reported as a line break). For an identifier that cannot be stored, `set` returns `Error::Store { "marker identifier <identifier, Debug form> cannot be stored: <reason>" }` and writes nothing, and `present` and `clear` return `Ok(None)` and `Ok(())` without touching a file (no marker can exist for it). The identifiers of real supplies (a UUID, a Bluetooth address, a BlueZ path, a HID path) can always be stored. `present(identifier)`: reads the marker file (`NotFound` is `Ok(None)`; any other read error is logged at WARN as `marker ignored <path>: unreadable` and `Ok(None)`); the content is split into lines after `trim_ascii` and must have exactly two (reason `malformed` otherwise); the first must be ASCII digits parsed as `u64` (reason `not a number`), the second must equal `identifier` (reason `identifier mismatch`, the file left alone, since it belongs to another identifier whose name collided); `UNIX_EPOCH.checked_add(seconds)` (reason `out of range`); a file failing `malformed`, `not a number` or `out of range` is logged at WARN, removed (a removal error is logged too) and `Ok(None)`; sub-second precision is not kept. `set(identifier, at)`: `at.duration_since(UNIX_EPOCH)` in whole seconds (a time before the epoch is written as 0) and the identifier, written with `write_atomic`, the directories created if needed, `Error::Store` on failure. `clear(identifier)`: removes the file, a missing file being `Ok`, any other failure `Error::Store`. | AR-033 | approved (rev 3) | SR-046 (revision 14): the marker holds the identifier and a timestamp, so the identifier is in the file and not only in its name; UR-030: a marker is advisory, so a corrupt one is dropped with a log line rather than an error. |
| DD-STORE-005 | `names::marker_name(identifier: &str) -> String` is pure: the first 32 characters (Unicode scalar values) of the identifier with every character outside `[A-Za-z0-9._-]` replaced by `_`, then `-`, then the 64-bit FNV-1a hash of the identifier's UTF-8 bytes as 16 lowercase hex characters. FNV-1a 64 is pinned as the on-disk format: offset `0xcbf29ce484222325`, prime `0x100000001b3`, `h = (h ^ u64::from(b)).wrapping_mul(PRIME)` per byte (`wrapping_mul` and `^` pass the arithmetic lint). Two different identifiers get different names unless the hashes collide (probability 2 to the power of minus 64, and DD-STORE-004 then reports a mismatch rather than a wrong marker); the prefix keeps the file readable to a person; a Windows reserved name (`CON`, `NUL`) cannot occur because the name continues with `-<hash>`. | AR-033 | approved | A Bluetooth identifier is a UUID; a HID path on Windows can be 200 characters with characters no file system accepts (device-model.md 1 names both kinds). The constants are pinned because changing them later would orphan existing markers. |
