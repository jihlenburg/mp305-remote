# DD: the Python library (`mp305-py` and the `mp305` package)

Status: approved (G4 py, user, 2026-10-01, revision 2; revisions 3, 4 and 5 approved 2026-10-02); revision 6 drafted, approval pending

Refines AR-040 of [3-architecture.md](../3-architecture.md) (approved at
G3) and the Python parts of AR-001, AR-003, AR-004, AR-018, AR-042 and
AR-050. The library is a thin synchronous face on `mp305_core::session`
(session DD revision 5): the native module `mp305._native` (the Rust crate
`mp305-py`, PyO3 0.29) holds the runtime, the blocking wait, the feed that
buffers the session's events, the safety calls, the log bridge and the
conversions; the pure Python package `mp305` holds everything a user
reads: the `Mp305` class, the typed readings and events, the exceptions,
the checks that run before any native call, and the helpers `stream()`,
`to_csv()` and `ramp()`. No protocol knowledge and no device rule lives
here; those are `mp305-core`'s and are tested there (the supply's range
and the scan bounds come from the core's constants). Coverage targets:
90 % of lines for the pure Python code (ADR-0008); 80 % of lines for the
binding crate, measured through the Python tests (section 8, decision 2).
Revision 2 resolves the review of revision 1; the concurrency and lifetime
model was redesigned as a whole.

Layout. Rust: `crates/mp305-py/build.rs` and `src/` with `lib.rs` (the
`#[pymodule(name = "_native")]`), `runtime.rs`, `wait.rs`, `feed.rs`,
`safety.rs`, `errors.rs`, `convert.rs`, `session.rs`, `discover.rs`,
`csv.rs`, `mock.rs`, `logbridge.rs`. Python: `python/mp305/` with
`__init__.py`, `errors.py`, `types.py`, `_checks.py`, `_logs.py`,
`device.py`, `helpers.py`, `testing.py`, `_native.pyi`, `py.typed`.
Tests: `tests/unit/` (pytest, one `@pytest.mark.spec("UT-PY-nnn")` per
test; section 8, decision 4) and `#[cfg(test)]` modules next to the Rust
code. Every Rust source file starts with `//! Implements: DD-PY-nnn`,
every Python module with a docstring naming its DD items.

Dependencies. Rust: `pyo3` 0.29 with the feature `abi3-py310` only (the
deprecated `extension-module` feature is not used, DD-PY-063),
`pyo3-build-config` 0.29 as a build dependency (feature `resolve-config`),
`mp305-core` with its `mock` feature (decision 1), `tokio` (features
`rt-multi-thread`, `time`, `sync`, `macros`), `futures` (for
`FutureExt::now_or_never`), `directories` 6, `log`; dev dependency `tokio`
with `net` (UT-PY-021). Python: no run-time dependency; development uses
`maturin` 1.9.4 or later, `pytest`, `pytest-cov`, `ruff` and `mypy`
through `uv`.

Terms: "attached" means holding the GIL, "detached" having released it
with `Python::detach`; "a blocking call" is a native function that waits
for the core through `wait::block` (DD-PY-002); "a slice" is one turn of
that wait, at most `WAIT_SLICE` (100 ms); "the feed" is the per-session
buffer of events and "the forwarder" the Tokio task that fills it
(DD-PY-007); "the dispatcher" is the Python callable `Mp305._handle` that
a blocking call receives as its `dispatch` argument; "the pump" is what a
blocking call does between slices: deliver queued log records, then
dispatch events (DD-PY-003); "a safety call" is `output_off` or `close`
(DD-PY-008); "terminal" link states are `lost`, `denied` and `closed`.
`Optional[X]` stands for the PEP 604 union of `X` and `None` in the
shipped annotations.

## 1. Runtime, blocking calls, the feed and the pump (Rust)

The concurrency and lifetime model as a whole (the items give the
details):

1. Threads. Python code runs only on Python threads. The two runtime
   workers run only Rust: the session and link tasks, the forwarder, the
   safety tasks and the log producer. Nothing reachable from a spawned
   task attaches to the interpreter.
2. Entering the runtime. Every native function that touches a session,
   the feed or the runtime first takes `runtime::enter()` on the calling
   thread (DD-PY-001). A blocking call polls its future inside `block_on`
   on the calling thread, detached, in slices (DD-PY-002); spawned work
   runs on the workers.
3. Locks. Leaf locks guard plain Rust data for a copy or a push and are
   never held across an `.await`, a `detach` or a call into Python. The
   only state held while Python code runs is the dispatch token and the
   log token, which are never waited for. No lock is held across the
   released-GIL wait (DD-PY-003).
4. Ownership. `Mp305` owns the native session; the native session owns
   `Arc`s of the core session and the feed and holds no Python object, so
   no reference cycle passes through native code. A safety task holds its
   own `Arc` of the core session until its sequence ends (DD-PY-008,
   DD-PY-009).
5. Ctrl-C. Raised within one slice, on the main thread only. It drops the
   future of a control call, which cancels the command (DD-SESS-003); it
   ends only the wait of `output_off` and `close`, whose sequences finish
   on the runtime, and the process waits for them at exit unless
   interrupted again (DD-PY-008); during `connect` it starts the close in
   the background and propagates at once (DD-PY-040).
6. Ends. `read()`, `readings()` and `stream()` decide on the core link
   state: `closed` ends them (`read` raises), `lost` raises
   `LinkLostError` with the loss text after everything queued before it
   was yielded, `reconnecting` waits (DD-PY-042, DD-PY-044, DD-PY-050).

## 9. Unit test specification

Python tests live in `tests/unit/test_*.py` (decision 4, DD-PY-064),
each with `@pytest.mark.spec("UT-PY-nnn")`, and run on
`Mp305._from_mock` through the `mock_device` fixture with

its own identifier (its UT ID and the case letter, for example
`"UT-PY-012-a"`), since the registry is process-wide (DD-SESS-052); no
test uses the default state directory. On a `ble` script the first control
call of a connection sends the `remoteCon` 2 request before its command
(DD-SESS-020, DD-SESS-021), unless a guard refuses the call first
(DD-SESS-032: link state, range, mode, fault, user limit): a script that leaves a command unanswered or
rejected still answers the request first with a reply entry `C9 00`,
`repeat: 1`, and counts of `0xC8` frames below include the request. The
mock runs on the real clock: mock delays are milliseconds, and a test
that waits for a core bound takes that long (1 s per reply timeout, 0.5 s
per output-off timeout, 5 s per reconnection tick); waits are conditions
polled every 20 ms with an upper bound, not fixed sleeps (except where a
test checks that nothing happens within a window), and no expected result
rests on a real-clock margin below 300 ms. Subprocess tests run
`subprocess.run([sys.executable, "-c", code], timeout=30)`; the child
raises the signal with `signal.raise_signal(signal.SIGINT)` from a daemon
`threading.Timer`, catches the `KeyboardInterrupt` unless the test says
otherwise, prints its observations as one JSON line and exits normally,
so its coverage is written. `caplog` captures logging. `rec` or
"the record" is a `testing.MockRecord` passed to `_from_mock` (or the one
`mock_discovery` exposes); where a test calls `_native.Session.from_mock`
itself it passes `rec.handles`. "Sent" means `rec.sent()` (or
`_mock_sent()`) filtered to the named opcode; the
fields of a sent `0xC8` are read by the test helper `tests/unit/frames.py`
from the payload layout of `protocol::ops::control` (`remoteCon` at 0,
`set_voltage` at 1 and 2, `set_current` at 3 and 4, `output` at 8, little
endian). Rust tests live next to the code under `#[cfg(test)]`.
