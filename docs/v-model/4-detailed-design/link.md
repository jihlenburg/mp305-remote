# DD: link module of `mp305-core`

Status: approved (G4 link, user, 2026-10-01, revision 2)

Refines AR-020, AR-021 and AR-022 of
[3-architecture.md](../3-architecture.md) (approved at G3), and takes its
clock rule from AR-003, its numbers from AR-014 and its error variants from
AR-050. Device facts cite
[docs/research/device-model.md](../../research/device-model.md) with their
evidence labels (code, hardware, inferred). The module sits between
`session` and one `Guarded` transport. It owns the one request in flight,
the two-level queue, the deferred expectations, the poll, the USB keepalive
and the loss detection, and it turns every incoming frame into exactly one
of: the reply to the request in flight, the completion of an expectation, a
device event, a late reply, or a counted and logged stray. It knows opcodes
and their reply opcodes but not what the payloads mean, with one exception:
it parses `0xC3` because it delivers readings. Coverage target 85 %
(ADR-0008, "rest of `mp305-core`"); nothing in this module needs a device,
so nothing is excluded. Revision 2 resolves the independent review of
revision 1 (LOGBOOK, "Link design review").

Rust module tree: `mp305_core::link` with the submodules `class` (pure:
request classes, eligibility and the dispatch decision), `queue` (pure: the
two-level queue), `task` (the loop that owns the `Guarded`) and, under
`cfg(test)`, `tests` (the task tests). The public handle `Link`, the
`Events` receiver, the outcome and event types live in `link/mod.rs`; the
two error variants in `error.rs`. Every source file starts with
`//! Implements: DD-LINK-nnn, ...`.

Terms used below. "Free" means no immediate request is in flight. "The
write" is the `Guarded::send` call; "the write start" is the clock time
just before it. "Kind" is `Description::kind` of the guard, `Ble` or `Hid`.
The route of every frame is `Route::Ble(ops::route(opcode))` on a `Ble`
guard and `Route::Hid` on a `Hid` guard; `link` never sends on another
route. Hex in texts and logs is lowercase, two digits (`{:02x}`). "The
count" is the consecutive-timeout count of DD-LINK-023.

## 1. The handle and its types

| ID | Design item | Refines | Status | Rationale |
|---|---|---|---|---|
| DD-LINK-001 | `Link::start<T: Transport>(guard: Guarded<T>, connected_at: Instant) -> Result<(Link, Events), Error>` spawns the link task on the current Tokio runtime (`Handle::try_current()`; `Error::Transport { message }` when there is none) and returns the handle and the event receiver. `connected_at` is the instant the transport was connected; `session` passes it, and it is the origin of the bind bound (DD-LINK-010). `Link` is not generic: it holds the unbounded command sender, the `AbortHandle` of the task, the shared counters, the shared loss text (a `OnceLock<String>`), the kind and the description. Only `start` and the task are generic over `T`. The task owns the `Guarded`. There is no other constructor, so every frame that leaves `link` passed the guard's allowlist. Both channels (commands to the task, events from it) are unbounded, so neither side can stall the other. Dropping the `Link` aborts the task; the guard drops with it and the transport's own `Drop` releases the device (DD-TRANS-012, DD-TRANS-020); `Events` then yields `None`. | AR-020 | approved | The task and the handle split lets `session` await one request while the task keeps polling and dispatching. A bounded event channel that `session` failed to drain would stop the poll and, over USB, lose the link after 8 s (device-model.md 4.4). |
| DD-LINK-002 | The handle's API. `fn request(&self, frame: Frame) -> Requested` enqueues `frame` at normal priority at once (before the returned future is polled) and returns a future, `Send + 'static`, of `Result<Outcome, Error>`: `Outcome::Reply { frame, at }` when the reply arrived, with `at` the reply's arrival stamp; `Outcome::Deferred(Pending)` for a deferred class as soon as the frame was written. `fn output_off(&self, frame: Frame) -> Requested` enqueues at urgent priority; the frame must have opcode `0xC8` (else the future resolves at once with `Error::Protocol(Reason::WrongOpcode { expected: 0xC8, got })`), payload byte 0 (`remoteCon`) equal to 1 and byte 8 (`output`) equal to 0 (else `Error::Protocol(Reason::Value { field: "remoteCon" or "output", value })`); nothing is queued in those cases. It resolves with `Outcome::Reply` only. `fn set_polling(&self, on: bool)`; polling is off when the link starts. `fn counters(&self) -> Counters`. `fn description(&self) -> &Description`. `async fn close(self) -> Result<(), Error>` (DD-LINK-041). A `Requested` future dropped before its request was written cancels the request (DD-LINK-022); one dropped later has no effect on the link. When the task has ended, `request` and `output_off` return a future that resolves at once with `Error::LinkLost { text }`, the text being the reason that ended the link (DD-LINK-040) or "closed by the host" (DD-LINK-041); the same text is used when the task ends while a future waits. `Events::next(&mut self) -> Option<DeviceEvent>` (async) yields events in order and `None` after the last one. | AR-020, AR-021, AR-003 | approved | Enqueueing before the first poll gives a defined order to concurrent callers and lets `session` use the futures in a `select!` alongside `Events`. AR-026 says nothing but the bind frames goes out before `Allowed`, so the poll starts off and `session` switches it on. `output_off` is the only urgent request (AR-020); requiring `remoteCon` 1 and `output` 0 is what stops the priority from being borrowed for anything else, and a `remoteCon` 2 frame would not be an immediate request over Bluetooth anyway. AR-003: a request cancelled by Ctrl-C must not be applied later. |
| DD-LINK-003 | `Pending` is the handle of a deferred request: it implements `Future<Output = Result<(Frame, Instant), Error>>`, `Send + 'static`, and exposes `opcode()` (the request opcode) and `deadline()`. It resolves with the matching reply and its arrival stamp, with `Error::Timeout { opcode, after }` when the deadline passes, or with `Error::LinkLost` when the link ends first. Dropping a `Pending` does not cancel the expectation: a reply that arrives later still completes it, is delivered as `DeviceEvent::LateReply` and logged at WARN, so that `session` still learns of a grant or a denial it stopped waiting for. | AR-020 | approved | `session` awaits the bind and the remote request alongside its other work; the expectation must outlive a dropped future so that the device's answer reaches `session` in every case. |
| DD-LINK-004 | `DeviceEvent`, delivered through `Events`: `Reading { reading: RawReading, at: Instant }` for every well-formed `0xC3` that completed a `0xC2` (the poll's, the block's or an explicit one), with `at` the arrival stamp the transport gave it; `Device(DeviceFrame)` for `0xC5`, `0xDD`, `0xE5`, `0xEB` and `0xDB` (`protocol::ops::events::classify`); `LateReply { frame: Frame, at: Instant }` for a `0x19` or `0xC9` that completed no request and no awaited expectation; `LinkLost { reason: LossReason }` exactly once, as the last event. `LossReason { Disconnected, Transport(String), Unanswered }` with `Display` texts "the transport reported the link closed", "transport error: <text>", "three requests in a row went unanswered". `Counters { dropped_frames: u64, ignored: u64, late_replies: u64 }` is a snapshot of three atomic counters shared by the handle and the task: `dropped_frames` counts what `link` dropped (an `Item::Error` from the guard, a malformed `0xC3`, a malformed device frame); `Guarded::errors()` counts only the first of these and stays available. | AR-020, AR-021, AR-022 | approved | One event type for everything the device does on its own, and one for what it failed to do. SR-014: the reading keeps the arrival stamp. |

## 2. Request classes, eligibility, the queue and the dispatch decision (pure)

| ID | Design item | Refines | Status | Rationale |
|---|---|---|---|---|
| DD-LINK-010 | `class::Class::of(frame: &Frame, kind: Kind) -> Class`. `Deferred { reply: 0x19, bound: Bound::FromConnection(timing::BIND) }` for `0x18` whose payload byte 17 (the fast flag) is 0; `Deferred { reply: 0xC9, bound: Bound::FromWrite(timing::REMOTE_PROMPT) }` for `0xC8` whose payload byte 0 (`remoteCon`) is 2 on a `Ble` kind; `Immediate { reply: ops::reply_opcode(opcode), timeout: timing::REPLY }` for everything else, including `0x18` with the fast flag set, `0xC8` with `remoteCon` 2 on a `Hid` kind, `0xC2` and `0xE0`. `output_off` uses `Immediate` with `timing::OUTPUT_OFF_ACK`. Deadlines: `FromConnection(b)` is `connected_at + b`, `FromWrite(b)` is `write start + b`, both with `checked_add`, an overflow meaning already expired. A deferred request whose deadline has already passed is not written: its future resolves with `Error::Timeout` at once. | AR-020 | approved | device-model.md 3 and 5 (code): the fast bind is answered by the Bluetooth chip at once; the prompt bind and the Bluetooth remote request are answered when a person acts; over USB `remoteCon` 2 is granted at once. SR-009 measures the 30 s from the connection, hence `FromConnection`; SR-053 measures the 70 s from the request. A prompt bind after the 30 s cannot succeed (device-model.md 12). |
| DD-LINK-011 | `queue::Queue` holds two `VecDeque`s of `Queued { frame, class, responder }`: `push_urgent`, `push_normal`, `peek()` and `pop_front()` return the urgent head if any, else the normal head; `drain(error)` removes every entry and resolves each responder with a clone of `error`. `len()` and `is_empty()`. Nothing else reorders entries. | AR-020 | approved | The only priority rule of AR-020 is "output-off first"; a two-deque structure makes it impossible to express any other. |
| DD-LINK-012 | `class::dispatch(state, opcode) -> Disposition` is a pure function of the opcode and a `DispatchState { in_flight_reply: Option<u8>, open_expectations: &[u8] }`. In this order: `Reply` when `opcode == in_flight_reply`; `Expectation` when `opcode` is `0x19` or `0xC9` and appears in `open_expectations`; `Event` when `opcode` is one of `0xC5`, `0xDD`, `0xE5`, `0xEB`, `0xDB`; `Late` when `opcode` is `0x19` or `0xC9`; `Ignore` otherwise (this includes `0xE3`, `0xE9` and `0xEF`, which the device can send after a remote request in another mode, device-model.md 5, and which `link` never solicits). The task applies the disposition (DD-LINK-021). Because no request is ever written while an expectation for its reply opcode is open (DD-LINK-013), the first two rules never both apply; the order is still fixed so that a violation degrades to the safer reading. | AR-020 | approved | SR-017: the reply to the request in flight wins, then the deferred state, then the device's own frames. |
| DD-LINK-013 | Eligibility. `class::eligible(entry, state) -> bool` is a pure function that the send step (DD-LINK-022) applies to every candidate, urgent, normal or internal, before writing it. An entry is eligible when all of these hold: (1) no open expectation has the entry's reply opcode (for a deferred entry, its own reply opcode); (2) the entry's opcode is not `0xC8`, or the `0xC8` block (DD-LINK-023) is clear; (3) the entry's opcode is not `0xC2`, or `last_reply_at + timing::POLL_PAUSE` has passed or no `0xC3` has arrived yet. Rule 3 paces every `0xC2`: the poll's, the block's internal one, and an explicit one from `session`. | AR-020, AR-021 | approved | One test for every candidate closes the gap revision 1 had (the urgent head skipped the block). Rule 1 is what keeps a `0x19` or `0xC9` attributable: a fast bind written while a prompt bind is open would otherwise take the prompt's answer. SR-013 and IT-021: at least 100 ms after the previous reply for every `0xC2`. |

## 3. The task

| ID | Design item | Refines | Status | Rationale |
|---|---|---|---|---|
| DD-LINK-020 | The task is one loop over a `biased` `tokio::select!` with three arms in this order: `guard.recv()`; the command channel (`Request`, `OutputOff`, `SetPolling`, `Close`); `sleep_until(next_deadline)`, enabled only when a deadline exists. `next_deadline` is the earliest of: the in-flight deadline; every expectation deadline; the poll due time when polling is on, the link is free and the queue is empty; the keepalive due time when the kind is `Hid`, the link is free and the queue is empty. The bias means a frame already in the channel is dispatched before any deadline is handled, so a reply and its deadline falling in the same instant resolve as a reply. After each arm the loop runs the send step (DD-LINK-022) repeatedly until the link is not free or no candidate is eligible. A closed command channel (the handle was dropped without `close`) ends the task as DD-LINK-041 does, without a caller to answer. All times come from `tokio::time` (AR-003); every `Instant + Duration` uses `checked_add`, an overflow meaning already due. | AR-020, AR-021 | approved | One loop, one owner of the state; nothing is shared but the counters and the loss text. Including a due time only when its candidate could be sent is what stops the timer arm from firing on every turn while a request is in flight. |
| DD-LINK-021 | Applying a disposition (DD-LINK-012) to an incoming `Item::Frame`. `Reply`: if the reply opcode is `0xC3`, parse it with `telemetry::parse`; a parse error counts as a dropped frame, is logged at WARN (`dropped 0xc3: <reason>`), and the frame is dropped with the request still in flight; a good reading is delivered as `DeviceEvent::Reading`, `last_reply_at` is set to its `at`, and the `0xC8` block is cleared. For every reply opcode, the responder receives `Outcome::Reply { frame, at }` (an internal responder discards it), the count is reset, the slot is free, and `reply 0x<op> +<ms>` is logged. A reply that arrives after its request timed out is attributed to the next request with the same reply opcode if one is in flight by then, or ignored; this is accepted for `0xC3` and `0xE1` (a reading is stamped at arrival and is at most `timing::REPLY` old; the info does not change) and prevented for `0x19` and `0xC9` by DD-LINK-023. `Expectation`: the expectation is removed and its `Pending` resolved with `(frame, at)`; if the `Pending` was dropped, `DeviceEvent::LateReply` is delivered instead and `late reply 0x<op> (unawaited)` logged at WARN. `Event`: `classify` succeeds and the `DeviceFrame` is delivered; a `classify` error counts as a dropped frame and is logged; `Ok(None)` cannot occur for these five opcodes and is treated as `Ignore`. `Late`: `late_replies` grows, `DeviceEvent::LateReply` is delivered, `late reply 0x<op>` is logged at WARN, and for a `0xC9` the `0xC8` block is set. `Ignore`: `ignored` grows and `ignored 0x<op>` is logged at WARN. An `Item::Error` counts as a dropped frame (the guard already logged it) and changes nothing else; it never ends the link (section 7, decision 1, and the pending change to DD-TRANS-004). `Item::LinkClosed` ends the link with `LossReason::Disconnected` (DD-LINK-040) unless the task is closing. | AR-020, AR-022 | approved | SR-016: a malformed `0xC3` never becomes a reading and, dropped, lets the request time out as if nothing came, which is what keeps loss detection honest. Only `0xC3` is parsed here because only readings are produced here; every other payload is `session`'s to parse. |
| DD-LINK-022 | The send step, run when the link is free and the task is not ending. The candidates, in order, the first eligible one (DD-LINK-013) wins: (1) the urgent head; (2) an internal `0xC2` when the head of the queue (urgent or normal) is a `0xC8` that is ineligible only because of the block; (3) the normal head; (4) the poll's `0xC2` when polling is on; (5) the keepalive `0xE0` when the kind is `Hid` and `last_sent_at + timing::USB_KEEPALIVE` has passed. An ineligible head blocks its queue; nothing behind it is considered. A queued entry whose responder is closed (its `Requested` future was dropped) is removed without being written and `cancelled 0x<op>` is logged at DEBUG; an `output_off` is written even if its future was dropped. The chosen frame is written with `tokio::time::timeout(timing::REPLY, guard.send(frame, route))`; `last_sent_at` is set to the write start, which starts at the link's start. A write that returns `Error::Protocol` resolves the responder with that error and leaves the link as it was; a write that fails otherwise, or does not return within `timing::REPLY`, ends the link with `LossReason::Transport(text)` (DD-LINK-040), the text being the error's text or "the write of 0x<op> did not complete within 1.0 s". After a successful write of an immediate class the request is in flight with `deadline = write start + timeout`; of a deferred class the expectation `{ request opcode, reply, deadline }` is registered (DD-LINK-010) and the responder receives `Outcome::Deferred(Pending)`; `sent 0x<op> <immediate, deferred or output-off>` is logged. Queued normal requests go before the poll, so a caller that never stops issuing requests starves the poll; `session` issues few, and the loss rule (DD-LINK-023) does not depend on the poll. The loop awaits the write inline: nothing the device sends can arrive before the write it answers, and frames that arrive meanwhile keep their producer stamps (DD-TRANS-026) and are dispatched on the next turn, before any deadline (DD-LINK-020). A `Close` that arrives during a write is handled after it. | AR-020, AR-021, AR-003 | approved | The reply window is measured from the write start so that one immediate request occupies the link for at most `timing::REPLY` whatever the write took; with DD-LINK-023 that is what makes the 4 s bound of DD-LINK-042 hold. A cancelled setpoint that went out later would be AR-003's "cancels the pending request" broken. |
| DD-LINK-023 | Timeouts, the count and the `0xC8` block. When the in-flight deadline passes, the responder gets `Error::Timeout { opcode, after: timeout }`, the slot is free and `timeout 0x<op> after <ms>` is logged. Every immediate timeout, whatever its opcode and whoever asked for it (the poll, the keepalive, the block's `0xC2` or `session`), grows the count by one (`saturating_add`); reaching 3 ends the link with `LossReason::Unanswered` (DD-LINK-040). Any reply that completes an immediate request resets the count to 0; `set_polling` does not touch it. Deferred requests have no reply timeout and never touch the count. The `0xC8` block is set by the timeout of an immediate `0xC8`, by the expiry of a `0xC9` expectation (DD-LINK-024), and by a late `0xC9` (DD-LINK-021); it is cleared by a well-formed `0xC3` completing a `0xC2` that was written after the block was set (DD-LINK-021 clears it on any good `0xC3`, and since the block makes every `0xC8` ineligible, any `0xC2` in flight when a good `0xC3` arrives was necessarily written after the block was set or is the one whose `0xC3` arrives now). While the block is set no `0xC8` is written, urgent or not (DD-LINK-013), and the send step puts an internal `0xC2` first (DD-LINK-022, candidate 2), polling on or off. | AR-020, AR-022 | approved | AR-020: after a `0xC8` timeout or a late `0xC9`, a `0xC8` goes out only after one `0xC2`/`0xC3` cycle, so a late `0xC9` can only arrive during a poll and is attributed as late, never to a new `0xC8`. The supply processes requests one at a time (device-model.md 6, code), so once the `0xC3` of a `0xC2` written after the block arrives, every `0xC9` the old `0xC8` could produce has been emitted before it. The block applies to `output_off` too: the cycle costs one round trip (about 130 ms over Bluetooth, hardware) and the alternative is attributing a stale `0xC9` to the output-off, which SR-022 relies on as the acknowledgment. Counting every immediate timeout is what bounds the loss report whatever `session` sends (DD-LINK-042) and also catches a silent USB supply while polling is off, through the keepalive; it is the change to AR-022 and SR-028 recorded in section 7. |
| DD-LINK-024 | Expectations. At most one is open per reply opcode (DD-LINK-013 keeps a second one waiting in the queue). When an expectation's deadline passes it is removed, its `Pending` resolved with `Error::Timeout { opcode: request opcode, after: bound }`, `expectation 0x<op> timed out` logged, and, for a `0xC9` expectation, the `0xC8` block set. A reply completes an expectation as DD-LINK-021 says, logged as `expectation 0x<op> resolved`. | AR-020 | approved | SR-009 and SR-053: the bind and the remote request time out on their own bounds while the link goes on polling. AR-020's "after a `0xC8` timeout" covers the deferred `0xC8` too: a `0xC9` that arrives after the 70 s must not be taken for a later request's answer. |

## 4. The poll and the keepalive

| ID | Design item | Refines | Status | Rationale |
|---|---|---|---|---|
| DD-LINK-030 | The poll. When polling is on, the poll's `0xC2` is a candidate whenever the link is free and the queue is empty; DD-LINK-013 rule 3 makes it eligible from `last_reply_at + timing::POLL_PAUSE`, or at once when no `0xC3` has arrived yet or the last `0xC2` timed out (`last_reply_at` is only ever moved forward by a good `0xC3`). An explicit `0xC2` from `session` and the block's internal `0xC2` move `last_reply_at` the same way, so the next poll keeps its distance from that reply too. The poll's responder is internal: its `0xC3` becomes a `DeviceEvent::Reading` (DD-LINK-021), its timeout counts (DD-LINK-023), and nobody else is told. `set_polling(false)` stops future polls; a poll in flight completes normally. `poll on` and `poll off` are logged. | AR-021 | approved | SR-013: no earlier than 100 ms after the previous reply, measured from the arrival stamp; one Bluetooth cycle is about 225 ms (hardware), so at least 2 readings per second follow. |
| DD-LINK-031 | The keepalive. On a `Hid` kind only, an `0xE0` is a candidate when `last_sent_at + timing::USB_KEEPALIVE` has passed, the link is free and the queue is empty; `last_sent_at` starts at the link's start, so with polling off the first keepalive goes out 2 s after `start`. Its responder is internal: the `0xE1` is consumed and its timeout counts (DD-LINK-023), logged as `keepalive`. On a `Ble` kind the keepalive never fires and `link` sends nothing on its own except the poll. While polling runs on `Hid`, the poll's writes keep `last_sent_at` within `timing::REPLY + timing::POLL_PAUSE` and the keepalive never fires. | AR-021 | approved | SR-051 and device-model.md 4.4 (code): 8 s of USB silence drops the link and the grant; 2 s leaves room for a stalled reply plus the poll pause. Counting its timeouts is what lets a silent USB supply be declared lost while polling is off. |

## 5. Loss and close

| ID | Design item | Refines | Status | Rationale |
|---|---|---|---|---|
| DD-LINK-040 | Ending the link on loss, with `reason`, in this order: (1) the in-flight request if any, the entry whose write just failed if any, every open expectation and every queued entry are resolved with `Error::LinkLost { text: reason.to_string() }` (the queue through `drain`); (2) polling and the keepalive stop; (3) the reason text is stored where the handle reads it (DD-LINK-002); (4) `DeviceEvent::LinkLost { reason }` is delivered and the event sender dropped, so `Events` yields `None` after it; `lost: <reason>` is logged; (5) the guard is moved into a spawned task that awaits `guard.close()` under `timeout(timing::REPLY)` and ignores the result; (6) the task returns. Nothing is written after step 1 begins. The causes are exactly those of DD-LINK-021 (`Item::LinkClosed`), DD-LINK-022 (a failed or overlong write) and DD-LINK-023 (the count reaching 3). | AR-022 | approved | AR-022 and AR-029: nothing issued before the loss is replayed; the caller of each request learns that it was lost. The event goes out before the close so that a transport whose disconnect hangs (a dead Bluetooth peripheral) cannot delay the report. Closing the guard releases the OS handle so that a reconnection (AR-029) can open a fresh one. |
| DD-LINK-041 | `close(self)`: the handle sends `Close` with a responder and awaits it. The task drains the queue and resolves the in-flight request and the expectations with `Error::LinkLost { text: "closed by the host" }`, stops the timers, stores that text, drops the event sender without a `LinkLost` event, awaits `guard.close()` under `timeout(timing::REPLY)` (`Error::Transport` on expiry) and answers the caller with the result; `closed` is logged. A `Close` is handled after a write in progress (DD-LINK-022). Dropping a `Link` without `close` aborts the task (DD-LINK-001). | AR-022 | approved | `session` runs the SR-029 sequence before calling `close`; a `close` with something queued is a caller's mistake, reported to that caller rather than hidden. |
| DD-LINK-042 | The 4 s bound of AR-022 and SR-028 (`timing::LINK_LOSS_REPORT`), by analysis. Let `t` be the arrival of the last reply of any kind. Any immediate request written at or after `t` occupies the link for exactly `timing::REPLY` from its write start (DD-LINK-022) and, unanswered, grows the count (DD-LINK-023); a deferred request frees the link at once and a refused write costs no time. With polling on, the link is never idle for longer than `timing::POLL_PAUSE` after `t` (the poll becomes eligible at `t + 0.1 s`; other candidates are eligible at once). So the third consecutive timeout falls at `t + 3 × REPLY` at the earliest and `t + POLL_PAUSE + 3 × REPLY = t + 3.1 s` at the latest, and `LinkLost` is delivered in the same loop turn, within `LINK_LOSS_REPORT`. With polling off the bound holds over USB through the keepalive (`t + 2 s + 3 s` is outside the 4 s but SR-051 only asks for the keepalive, and SR-028 is stated for the polling state), and over Bluetooth loss is reported through the OS disconnect only. The block's internal `0xC2` and a queue head waiting on an expectation do not idle the link either: the block's `0xC2` is written at once, and a waiting head lets candidates 4 and 5 through. UT-LINK-017 verifies the loaded case. | AR-022 | approved | SR-028: "within 4 s of the last reply". Revision 1's analysis wrongly assumed a `session` request could delay the report by at most one window; without counting every timeout the delay has no bound. |

## 7. Changes to approved documents and decisions for G4

Revision 2 adopts the reviewer's recommendation on the three decisions of

## 8. Unit test specification

Tests of the pure parts live next to the code under `#[cfg(test)]`. The
task tests live in `crates/mp305-core/src/link/tests/*.rs`, compiled under
`#[cfg(test)]` as submodules of `link`, so that they reach `Frame::new`,
`telemetry::tests::C3_PAYLOAD` (the capture reading, cited there) and
`transport::test_log`. Each test names its UT ID. Tests run on a paused
Tokio clock (`#[tokio::test(start_paused = true)]`) and let sleeps
auto-advance it. The task tests use `transport::stub::Stub` wrapped in
`Guarded::new`: a channel the test feeds, a send delay, a record of sends
with their write-start times (readable after a 1 ms sleep), `fail_next_send`
and `closes()` (decision 5 above). "Feed X at t" means sending a
`RawIncoming { at: t, .. }` on the stub's channel at clock time t; "reply
each 0xC2 after d" means a test task that feeds a good `0xC3` d after each
`0xC2` the stub recorded. "A good 0xC3" is `C3_PAYLOAD`; other frames are
built with `Frame::new` from the layouts in `protocol::ops`. Unless a test
says otherwise the stub is `Ble`, its delay is 0, `connected_at` is the
link's start, and times are relative to the link's start.
