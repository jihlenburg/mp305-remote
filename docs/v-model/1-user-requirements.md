# 1. User requirements (UR)

Status: approved (G1, user, 2026-09-30)

The user requirements and the hazard list for the v1 remote control of the
ISDT MP305B bench power supply. The v1 scope was agreed in the conversation
of 2026-09-29 (TODO.md, "Agreed v1 scope"). Revision 8 rewrites the
requirements from the device firmware findings, as the user decided on
2026-09-30 (LOGBOOK, "Requirements go back to the drawing board"). Device
facts cite [docs/research/device-model.md](../research/device-model.md),
which carries the evidence label of every statement (code, hardware,
inferred), and [docs/research/protocol.md](../research/protocol.md). A fact
labelled "code" was read from the 1.6.0.51 update and has not yet been
checked on the user's unit, which reported 1.6.0.40.

"The software" means both products: the desktop app `mp305-app` and the
Python library `mp305`. "The supply" means the MP305B.

## 1. Hazards and functional safety (IEC 61508)

The MP305B delivers up to 30 V and 5 A (150 W) at its output. Its firmware
accepts setpoints up to 30.50 V and 5.100 A (device-model.md 9, code). A
wrong command, setpoint corruption, a missed state change or a missed fault
can destroy the device under test (DUT) or start a fire, causing direct
property damage and indirectly human injury. Under ADR-0008, this software
is treated as an electrical safety-related system according to IEC 61508.
Every hazard must be systematically mitigated and verified.

| ID | Hazard | Cause | Severity | Mitigation |
|---|---|---|---|---|
| H-001 | The output switches on without the user asking for it. | `0xC8` carries the whole output state, including on or off, and applies its fields one by one until the first invalid one (device-model.md 9, code). A command built from stale or default values switches the output. | critical | UR-004, UR-005, UR-023, UR-034; SR-012, SR-016, SR-017, SR-018, SR-019, SR-020, SR-021, SR-023, SR-040, SR-041, SR-042, SR-044, SR-045, SR-052 |
| H-002 | Commands reach a different supply than the user meant. | All units advertise the same name apart from three trailing characters derived from the unit's Bluetooth address (device-model.md 1, code; hardware for one unit). Over USB there is no serial number: the request stalls (code). | critical | UR-002, UR-010; SR-001, SR-003, SR-004 |
| H-003 | Voltage or current limit changes to a value the user did not choose. | The software sends remembered setpoints after a (re)connect, or a full-state `0xC8` undoes a change made on the front panel (device-model.md 9, code). A `0xC8` rejected after its voltage field still applies the voltage (code). | high | UR-004, UR-023, UR-024, UR-034; SR-012, SR-016, SR-017, SR-018, SR-019, SR-021, SR-028, SR-042, SR-044, SR-045, SR-052, SR-055 |
| H-004 | The output stays on after the software exits, crashes or loses the link. | The supply keeps the output as it was when the link drops and only releases remote control (device-model.md 4.4, code; hardware check TBD-005). A crashed host cannot send anything. Over USB the supply drops the link and the grant after 8 s of silence (code). | high | UR-006, UR-018, UR-024, UR-030, UR-031, UR-035, UR-037; SR-022, SR-028, SR-029, SR-030, SR-046, SR-047, SR-051, SR-054, SR-055. Mitigations chosen 2026-09-29: an unclean-exit warning (UR-030), a bench-safety note for unattended runs (UR-031) and the TBD-005 spike. Residual risk: a hard crash or a kill during a live output still cannot switch it off; UR-030 surfaces it on the next start. Accepted by the user on 2026-09-30 (TBD-015). |
| H-005 | The user reads or sets a value in the wrong unit or scale. | The protocol uses 10 mV, 1 mA, 10 mW and 0.1 Wh steps, and a signed temperature (device-model.md 8, code; setpoints hardware). Frames the supply sends on its own could be mistaken for replies (device-model.md 6, code). | high | UR-003, UR-012, UR-017, UR-034; SR-014, SR-015, SR-016, SR-017, SR-024, SR-025, SR-033, SR-040, SR-042, SR-044, SR-045, SR-052 |
| H-006 | Someone other than the person at the bench controls or watches the supply. | Reads, settings writes and table writes are not gated by the bind or by remote control (device-model.md 5, code; reads after a deny hardware). Remote control over Bluetooth needs a second confirmation on the supply; over USB it is granted without one (code, TBD-004, TBD-012). A remembered host reconnects without a prompt (code, TBD-006). | high | UR-008, UR-016, UR-032, UR-033, UR-036; SR-006, SR-007, SR-008, SR-009, SR-010, SR-011, SR-018, SR-023, SR-032, SR-049, SR-050, SR-053. Mitigations chosen 2026-09-29: the software refuses all control after a deny. The unguarded reads and writes are in the device and the software cannot close that gap; UR-033 keeps the software itself out of the unguarded writes. Residual risk accepted by the user on 2026-09-30 (TBD-015). |
| H-007 | A setpoint exceeds what the DUT can take. | Typing error, or a script with a wrong value. | high | UR-007, UR-012; SR-024, SR-025, SR-040 |
| H-008 | The output runs, or is switched on, while the supply reports a fault. | A protection trip (OCP, OVP, overheat, reversed output) goes unnoticed. The supply itself forces the output off while a fault is active and refuses output-on with `FF` (device-model.md 8, code). | critical | UR-009; SR-026, SR-027 |
| H-009 | The supply is left in its bootloader, factory reset, or with changed stored settings. | The maintenance opcodes and `FE AA 55` (factory reset with reboot), the profile and program writes that switch the output off and can leave the supply "busy", and the two opcodes that rewrite the Bluetooth chip's advertising data (device-model.md 7 and 11, code). | high | UR-025, UR-033; SR-006 |

## 2. User requirements

### 2.1 Core control and monitoring

| ID | Requirement | Parent or source | Priority | Verification | Status | Rationale |
|---|---|---|---|---|---|---|
| UR-001 | The software shall connect to an MP305B over Bluetooth LE and over USB HID. | user, conversation 2026-09-29; ADR-0004 | must | T | draft | Bluetooth is the everyday link. USB HID needs no confirmation on the supply and is the candidate for unattended runs (device-model.md 4.2, code, TBD-004). The supply serves one host at a time: a bound Bluetooth host detaches USB, and USB traffic silences Bluetooth for 8 s (device-model.md 4.3, code). |
| UR-002 | The software shall let the user choose the target supply explicitly, by an identifier that tells two supplies apart, and shall never pick a supply on its own when more than one is found. Over Bluetooth the identifier shall include the three trailing characters of the advertised name. | user, conversation 2026-09-29 (v1 scope: connect); H-002 | must | T | draft | The three characters come from the unit's Bluetooth address and differ between units unless the addresses collide (device-model.md 1, code). Over USB only the OS device path tells units apart; there is no serial (code, TBD-013). |
| UR-003 | The software shall take setpoints and show readings in volts, amperes and watts. | user, conversation 2026-09-29 (v1 scope: set voltage and current limit); H-005 | must | T | draft | Raw device units never reach the user. |
| UR-004 | After connecting, the software shall read the supply's setpoints, output state, mode, fault state and versions, and show them before it allows any control action. | H-001, H-003 | must | D | draft | The user sees what the supply is doing before touching it. The mode matters: control only works in the supply's live mode (device-model.md 7, code). |
| UR-005 | The software shall switch the output on only when the user explicitly asks for it. Connecting, changing a setpoint, or starting a recording shall never switch the output on. | H-001 | must | D | draft | Output on is always a separate, deliberate action. |
| UR-006 | The software shall provide an output-off action that is available whenever the supply is connected, allowed and in DC mode, including after the supply has taken remote control away, and has the supply accept the output-off command within 0.5 s. In any other mode it shall tell the user to switch the output off on the supply. | H-004; user, conversation 2026-09-29 (0.5 s) | must | T | draft | The quick way to make the bench safe. The limit applies to the supply's acknowledgment; how fast the voltage falls depends on the load. Taking remote control back over Bluetooth needs a confirmation on the supply (UR-036), so the action may involve the person at the bench. |
| UR-007 | The software shall let the user set a maximum voltage and a maximum current limit, and shall reject any setpoint above them without sending it to the supply. | H-007 | should | T | draft | A second guard for delicate DUTs. |
| UR-008 | Over Bluetooth, on a connection the supply does not recognise, the software shall tell the user to confirm the connection on the supply's screen and wait for the answer. If the supply does not report the connection as allowed, the software shall report the refusal and disconnect, without reading or controlling anything. | H-006; LOGBOOK 2026-09-29, "Hardware: deny test"; user, conversation 2026-09-29 (TBD-001) | must | T | draft | The supply asks allow or deny for a host it does not remember (device-model.md 4.1, code; hardware with WebLink's frame). There is no read-only mode after a deny. The supply drops an unbound link about 30 s after connecting (code, TBD-008), so the wait has a bound the software must tell the user about. |
| UR-009 | The software shall watch the supply's fault bits while connected, tell the user about every active fault as soon as it is reported, naming the fault, and refuse to switch the output on while any fault is active. | H-008 | must | T | draft | Fault bits 0 to 8 are defined; the supply forces the output off while any is active (device-model.md 8, code). How a trip shows in the readings on hardware is TBD-016. |
| UR-023 | When the user changes one setting (voltage, current limit or output state), the software shall leave every other setting as the supply currently reports it. | H-001, H-003 | must | T | draft | Protects changes made on the front panel. `0xC8` always carries all settings (device-model.md 9). |
| UR-024 | When the link to the supply is lost, the software shall tell the user at once that the output is still in its last state and that the supply has released remote control, and shall not reconnect or send any command until the user asks it to, unless the user enabled automatic reconnection for the session (UR-037). | H-003, H-004 | must | D | draft | The supply keeps the output and releases the grant on link loss (device-model.md 4.4, code, TBD-005). Automatic reconnection is opt-in per session (TBD-017, settled 2026-09-30). |
| UR-025 | The software shall not update the supply's firmware. | H-009 | must | I | draft | ISDT's WebLink and Polying do this. v1 stays out of the bootloader. |
| UR-026 | After connecting, the software shall show the supply's model, application version and hardware revision. | user, conversation 2026-09-29 (firmware update check); AGENTS.md, "Captures and firmware version" | should | D | draft | Both values come from the supply's main processor (device-model.md 1, code; hardware for the Bluetooth layout). Hardware test records must cite them. |
| UR-027 | When a search finds no supply, the software shall tell the user why that can be: the supply is off or out of range, another app such as WebLink or ISDT's Polying is connected to it, a USB host is talking to it, or remote control is disabled on the supply. | user, conversation 2026-09-29; LOGBOOK 2026-09-29, "Hardware: advertising test" | should | D | draft | The supply does not advertise in any of those states (device-model.md 1 and 4.3, code; connected elsewhere hardware). |
| UR-032 | Over Bluetooth, the software shall present a stable identifier of its own host at every bind, so that a supply which has allowed that host once recognises it again without asking the person at the supply. The software shall tell the user whether the supply recognised it. | H-006; user decision 2026-09-30 (rewrite from the firmware) | should | T | draft | The supply remembers up to five allowed host IDs and answers a repeat bind itself when the fast flag is set (device-model.md 3 and 4.1, code, TBD-006). A host-specific ID also keeps two hosts apart, which WebLink's constant ID does not. |
| UR-033 | Beyond the v1 control commands, the software shall not change anything stored in the supply: no settings, profiles, programs, language, or Bluetooth chip configuration. | H-009; user, conversation 2026-09-29 (v1 scope) | must | I | draft | Those writes are not gated by the bind or by remote control, and several switch the output off or leave the supply busy (device-model.md 7 and 11, code). An allowlist in the transport makes this checkable. |
| UR-034 | The software shall accept frames the supply sends on its own, and replies that arrive later than the request, without mistaking them for the reply to another request, and shall show a settings change made on the front panel when the supply reports it. | H-001, H-003, H-005 | must | T | draft | The supply sends `0xC5` and other frames unsolicited and answers bind and remote-control requests later (device-model.md 6, code). Matching by order would misread them (H-005) or attribute a stale `0xC9` (H-001). |
| UR-035 | Over USB, the software shall keep the link alive while it is connected, so that the supply does not drop the link and release remote control on its own. | H-004 | must | T | draft | The supply drops the USB link after 8 s without a frame (device-model.md 4.4, code). Releasing the grant leaves the output on with no one in control. |
| UR-036 | Over Bluetooth, when the software asks the supply for remote control, it shall tell the user to confirm on the supply's screen, wait for the answer, and report a refusal. Over USB no confirmation is needed. | H-006 | must | T | draft | The supply shows "Allow Remote Control" and answers later; while it waits, every control command is silent (device-model.md 5, code, TBD-012). Over USB the grant is immediate (code, TBD-004). |

### 2.3 Python library (`mp305`)

| ID | Requirement | Parent or source | Priority | Verification | Status | Rationale |
|---|---|---|---|---|---|---|
| UR-015 | The library shall offer a synchronous API to find and connect to a supply, set voltage and current limit, switch the output, and read measurements. | ADR-0006, ADR-0007 (proposed) | must | T | draft | Lab scripts and notebooks read most naturally with blocking calls. ADR-0007 still needs the user's approval. |
| UR-016 | The library shall raise a distinct exception type for each of: a setpoint out of range, a denied connection, a denied or lost remote control, a command the supply rejects, a timeout, and a lost link. | ADR-0007 (proposed); H-006 | must | T | draft | A script can then react to each case, for example stop a test run cleanly. The remote-control case is separate from the bind case because the supply decides them separately (device-model.md 5). |
| UR-017 | The library shall return each reading as a typed object with voltage, current and power in V, A and W as floats, plus output state, regulation mode and active faults. | user, conversation 2026-09-29 (v1 scope: read voltage, current, power, CV/CC); H-005, H-008 | must | T | draft | Scripts compare and log values without knowing the protocol's raw units. |
| UR-018 | The library shall provide a context manager that switches the output off and releases remote control when the block ends, also when it ends with an exception. | H-004 | should | T | draft | A crashing script still leaves the bench safe, as long as the Python process itself survives. |
| UR-028 | The library shall stream readings at a rate the user chooses and write them to a CSV file with a helper. | user, conversation 2026-09-29 (v1 scope) | must | T | draft | The library gets streaming and CSV logging but no chart. |
| UR-029 | The library shall provide a helper that ramps the voltage or the current limit from a start value to an end value in steps, driven from the host. | user, conversation 2026-09-29 (v1 scope, nice to have) | could | T | draft | The supply's own program mode and its ramp setting are out of v1 scope. |
| UR-030 | While the software holds remote control with the output reported on, it shall keep a persistent marker naming the supply and the time. On its next start, before any control action, it shall warn the user if a marker for the supply being connected shows a previous session that did not end with the output switched off. | H-004; user, conversation 2026-09-29 (TBD-015) | should | T | draft | A crash or a lost link leaves the output on (device-model.md 4.4, code). The marker turns a silent stuck-on output into a warning the next time the user connects. It does not switch the output off by itself. Verification is T: the marker and the warning are testable through the library's exposed state, while the app side is demonstrated. |
| UR-031 | The user documentation of the app and the library shall carry a bench-safety note for unattended runs: set a hardware current limit and OCP mode on the front panel, keep only a safe load on the output, know that the supply keeps the output on when the link drops, and prefer USB over Bluetooth for unattended runs. | H-004; user, conversation 2026-09-29 (TBD-015); user decision 2026-09-30 (TBD-017) | should | I | draft | The software cannot switch the output off after a crash, so the last line of defense is how the bench itself is set up. USB needs no confirmation on the supply, no bind window and no radio (device-model.md 4.2, code). |
| UR-037 | The user shall be able to enable automatic reconnection for a session. When it is enabled and the link is lost, the software shall reconnect to the same supply, using the remembered host over Bluetooth, read the supply's state again before anything else, and shall not take remote control or change the output until the user acts again. When it is disabled, UR-024 applies. | H-003, H-004; user decision 2026-09-30 (TBD-017) | should | T | draft | An unattended log run should survive a short link loss. Re-taking control silently could surprise a person at the bench, so control stays with the user. Over Bluetooth this needs the remembered host (UR-032, TBD-006). |
